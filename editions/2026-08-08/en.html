Background

Bitcoiners Turn to Dice Throws After Coldcard Entropy Bug

A critical firmware vulnerability in Coldcard hardware wallets, introduced in version 4.0.1, caused seed generation to use the weak Yasmarang PRNG instead of the STM32 hardware TRNG, leading to Bitcoin thefts beginning July 30. In response, Bitcoiners are increasingly relying on physical dice throws to generate seed entropy and re-evaluating their self-custody setups. This incident undermines trust in hardware wallets and shows that even widely used devices can harbor opaque, catastrophic bugs. It has pushed the community toward 'don't trust, verify' practices such as dice entropy and cross-checking derived addresses. Coinkite estimates that Mk2 and Mk3 devices produced only about 40 bits of entropy, while Mk4, Mk5, and Q devices reached about 70 bits — well below the 128 bits required for a secure 12-word seed phrase. The vulnerability was introduced when a firmware rewrite moved from a GPL model to a read-only model and began using MicroPython's Yasmarang PRNG.

rss · Cointelegraph · Aug 7, 21:00

Background, discussion, and references

Background

Hardware wallets generate private keys from a seed phrase, and their security depends on true randomness. A TRNG uses physical processes such as electronic noise to produce unguessable numbers, while a PRNG is deterministic and can be predicted if its seed is known. Physical methods like dice throws provide auditable entropy that does not rely on the wallet's internal random number generator.

Assembly Hall of Shame Showcases Bizarre x86 Instruction-Timing Tricks

Security researcher xoreaxeaxeax has published the Assembly Hall of Shame, a GitHub repository collecting bizarre and extreme x86 instruction-timing measurements and low-level timing tricks. The project quickly gained traction on Hacker News with 383 points and 94 comments. This work shines light on obscure x86 behaviors that matter for low-level programmers, OS developers, and security researchers. Understanding such timing anomalies can help in side-channel research, firmware security, and hardening against SMI-related latency attacks. The repository includes leaderboard-style timing results, with a current notable entry being a ~12 ms write to an ACPI I/O port that may actually be trapping into System Management Mode (SMM). The project rules exclude timing the handler of trapped, emulated, or virtualized instructions, so the true SMI overhead remains a disputed edge case.

hackernews · piotrgrabowski · Aug 8, 02:01 · Discussion

Background, discussion, and references

Background

SMI (System Management Interrupt) is a special CPU interrupt that switches the processor into System Management Mode, a privileged firmware environment typically used for power management, hardware emulation, and system control. Because the OS cannot predict or control when an SMI arrives or how long SMM handling takes, SMIs can cause irregular latency spikes in real-time systems. Instruction-timing variations on x86 are also known to enable microarchitectural side-channel attacks, making projects like this useful for security research.

Discussion

Commenters point to related work such as smiiiiiiiiiiiiiiii, which uses slow instructions to break SMI, and note that old CPUs like the MC68000 could lock up forever waiting for a missing bus acknowledgement. Several users suspect the 12 ms ACPI I/O port write is really trapping to SMM, while others highlight the author’s other projects and the idea of Turing-complete x86 page-table tricks via trapcc.
